# DA2 Base TensorRT FP16 isolated test

2026-11-05. User-requested FP16 test following the AMP/quantization review.
No application defaults, artifact allowlists, runtime dependencies or installed
FP32 engines were changed. These are local experimental engines, not a release.

## Method

- RTX 5090, driver 621.14, TensorRT 11.2.1.2, PyTorch 2.7.1+cu128.
- Reused the trusted fixed-position FP32 ONNX for `(1,3,518,924)`, SHA256
  `3c7912b2934004626e1e5cbfb6b3ee0446909bd20a411cf8709e324220f945b2`.
- Explicit ONNX FP16 conversion using the existing onnxruntime converter;
  FP32 input/output, Resize, LayerNormalization and Softmax retained. TF32 off,
  builder workspace limit 2 GiB. No application package upgrades.
- `mixed`: broadly converted remaining operators to FP16.
- `selective`: only MatMul/Conv/ConvTranspose eligible; attention and final
  output_conv2 excluded. Residual and other operators remain FP32 in the graph.
  This differs from the earlier FP32-encoder/FP16-head experiment.
- Production FP32 control loaded through the existing hash-enforcing loader.
  Newly built plans hash-checked against their build result before loading;
  exact tensor names, dimensions, directions and FP32 I/O checked.
- Same resident input, owned CUDA stream, ten warmups per engine then sixty
  alternating-order CUDA event measurements per engine. Timings exclude capture,
  preprocessing, output resizing, depth postprocessing, stereo and presentation.
  All three engines coexist during the matched measurement.
- Official pinned PyTorch FP32 oracle is the numerical reference. Public fixtures
  retain existing hash verification: 60 consecutive frames each of FloorballGame,
  OfficeWalk and ParkingGarage, plus black/gray/white and the first Floorball frame
  resized to 2560x1080, 1080x1920 and 3840x2160. Total **186 inputs per engine**.
- All cases use the 518x924 canvas. Resized inputs exercise preprocessing/padding
  on that canvas; this is not coverage of the other 518x896 production profile.
- Historical raw-depth threshold unchanged: `atol=0.001, rtol=0.001`.
  No new perceptual acceptance threshold was established after seeing results.

## Results

| Engine | Median model GPU time | Ordered sample p10–p90 | Relative model speed | Finite | Historical raw-depth pass |
|---|---:|---:|---:|---:|---:|
| Production FP32 | 25.319 ms | 25.031–27.552 ms | 1.00x | 186/186 | 186/186 |
| Mixed FP16 | 4.204 ms | 4.159–4.245 ms | 6.02x | 186/186 | 0/186 |
| Selective FP16 | 5.351 ms | 5.308–5.749 ms | 4.73x | 186/186 | 0/186 |

These speed ratios are **model-only**, not application FPS or end-to-end latency.
The FP32 value differs from the earlier AMP probe's 23.37 ms; the comparison above
uses its own matched control, not a cross-run denominator. Sample percentiles are
ordered observations, not confidence intervals or long-session evidence.

| Engine | Maximum public-frame MAE | Maximum public-pixel absolute difference | Maximum public-frame MAE / reference p2–p98 range |
|---|---:|---:|---:|
| Production FP32 | 0.00001157 | 0.0009413 | 0.000000911 |
| Mixed FP16 | 0.008172 | 0.434489 | 0.00062272 |
| Selective FP16 | 0.006524 | 0.364548 | 0.00051781 |

Depth values are relative, not meters. Range-normalized MAE is a numerical proxy,
not a percentage of visible quality loss. Selective FP16 improves these public
frame maxima but is **not uniformly more accurate**: the portrait case MAE is
0.017138 versus mixed FP16's 0.010350; constant white is also worse. The broad
candidate's maximum MAE across all cases is 0.010350, selective's is 0.017138.
Neither candidate qualifies as a behavior-preserving replacement under the
existing raw-depth contract. Failing that contract alone does not establish
visible degradation or make a different quality/speed tradeoff invalid.

The engine inspector reports Half tensors in both compiled plans (mixed: 371
Half / 18 Float layer I/O occurrences; selective: 326 Half / 96 Float). These
counts verify mixed precision is present; they are not operation, FLOP or
accumulator-precision percentages. Engine I/O remains FP32.

## Interpretation and limits

Actual TensorRT FP16 shows a substantial model-time benefit, unlike the earlier
PyTorch AMP swap. Both candidates merit a separately identified app experiment.
Before a default change, measure full native SBS output and temporal/edge/RGB
differences, with a predeclared quality-comparison contract. Neither broad nor
selective FP16 is established as the quality winner. The other input profile,
actual live capture/lifecycle, sustained playback, physical display and binocular
quality remain untested for these plans. Consecutive depth samples here do not
constitute temporal-stereo quality validation. RowFlow viewing remains deferred.
