# Small FP16 + VFG 실사용 시험 — 2026-11-06

## 구현

`Run-Compare-Small-VFG.cmd`가 DA2 Small FP16 + NVIDIA Medium 2x VFG를 연다.
기존 `Run-Compare-Small.cmd`는 VFG 없는 비교 기준이다. 두 실행기는 입체감
0.5, 출력 무제한, 최신 깊이 범위 안정화·coverage, Owl3D용 독립 출력 창과
출력 재캡처 거부를 공유한다. 입력 선택과 시작은 사용자 명시 동작이다.
일반 앱 기본에 VFG를 켜거나 추가 설정을 노출하지 않았다.

VFG 출력 버퍼/생성/발행/수명은 `VfgOutputMixin`으로 공통화했다. Small은
기존 `LiveSmallGpuInput`의 GPU cubic 전처리, 518×518 FP16 추론과 후처리를
상속한다. Base는 기존 source-depth 경로를 유지한다. Small의 raw CUDA stream은
기존 비소유 Torch wrapper로만 참조하며, 할당 스트림 일치를 검사한다.
모델별 DLL 및 공통 bridge/SDK 해시 검사는 유지했다. 네이티브 바이너리나
모델을 변경할 필요는 없었다.

Small adapter는 worker에서 지연 로딩한다. 실행기 import만으로 TensorRT를
불러오지 않는 독립 프로세스 검사도 추가했다. 원본·생성 프레임의 시각/ID와
출력 슬롯 반환 규칙은 공통이다. 빠른 Small에서 WGC compositor stamp가
완료 시각보다 앞설 수 있어 VFG timeline도 실제 source/ready를 그대로
기록하고 둘 이후로 발행을 예약한다. 100ms 초과 시각 선행은 거부하며,
컷/잘못된 source 간격에서는 생성하지 않는다. 시각을 덮어쓰거나 음수 지연을
0으로 고치지 않는다.

## 실제 측정

RTX 5090/Windows, 공개 FloorballGame 창, Small FP16, 입체감 0.5,
`range` 정책, 무제한 출력. 각 실행은 4초 워밍업 뒤 4초 구간을 5회 측정했다.
표는 각 구간 수치의 중앙값이다. 1080p 입력은 3840×1080 Full SBS,
4K 입력은 7680×2160 Full SBS이며, 화면에는 1400×650 창으로 맞춰 표시했다.
실제 WGC→SBS→네이티브 Qt 완료를 측정했지만 모니터 물리 표시나 1:1 scanout,
장시간 게임 성능은 아니다. 모델·SBS·출력·동시 시스템 부하를 포함한다.

| 입력 / 실행 | 출력 FPS | 원본 SBS FPS | 생성 FPS | 원본 source→Qt P50 (ms) |
|---|---:|---:|---:|---:|
| 1080p / Small | 70.73 | 70.73 | 0 | 17.00 |
| 1080p / Small VFG | 102.92 | 51.46 | 51.46 | 28.24 |
| 4K / Small 첫 실행 | 28.91 | 28.91 | 0 | 41.72 |
| 4K / Small VFG 일반 실행 | 56.11 | 27.93 | 28.18 | 55.38 |
| 4K / Small 반복 | 38.43 | 38.43 | 0 | 31.07 |
| 4K / Small VFG 반복 | 35.30 | 17.65 | 17.65 | 82.03 |

1080p 출력은 약 45.5% 증가했으나 원본 SBS 처리량은 약 27.2% 줄었고,
지연은 약 11.2ms 늘었다. Small도 VFG 비용과 출력 대기의 영향을 받는다.
4K는 baseline부터 차이가 크고 VFG 반복에서 역전됐다. 변동 원인은 분리하지
못했으며, 56 FPS만 골라 일반 성능 개선이나 4K60 달성으로 보고하지 않는다.
각 열을 독립적으로 중앙값 계산하므로 원본+생성이 출력과 조금 다를 수 있다.

별도 4K 수명/컷 실행(`4k-b`)은 15번째 원본마다 강제 컷을 넣었으며 출력
31.18 FPS, 원본 16.22, 생성 14.97, 지연 83.33ms였다. 일반 성능 비교와 섞지
않았다. 강제 컷뿐 아니라 실행 시점의 부하가 달라 이 차이를 컷 비용으로
단정하지 않는다. 프로세스 private 메모리는 1080p 약 2.11→3.13GiB,
4K 약 2.62→6.47GiB였다. GPU VRAM 측정값은 아니다.

## 검증

- 비교/시간 처리 단위 검사 **12개 통과**: 모델별 추론 경로 보존, 공통 출력,
  잘못된 모델/타임스탬프/슬롯 거부, future source/midpoint의 실제 시각 보존,
  TensorRT 지연 import 포함.
- Small과 Base 각각 1080p·4K 3프레임씩, 총 **12개 원본/네이티브 정확 일치**.
  각 모델 두 크기에서 VFG 생성 실행 및 RGBA 저장 성공. 공개 영상 세 장의
  원본 동등성 검사이며, 보간 화질 개선의 정답 비교로 해석하지 않는다.
- 실제 Small VFG와 Base VFG GUI에서 기본 0.5, `range`, 명시적 시작, 원본/생성
  프레임 집계, 보호된 제어/오류창과 캡처 가능한 출력, 프로세스 간 출력 재캡처
  거부, 두 모니터 이동/F11/숨김·복원/중지·재시작/닫기 통과.
- Small VFG 4K lifecycle: 숨김·복원, 1280×720 크기 전환, 재시작, 준비 중 취소,
  강제 컷에서 원본만 출력 통과. worker 생성/해제 수 2/2, 재시작 1/1,
  준비 중 취소 0/0. 종료 후 native pool/node 0, 잔류 프레임 없음.
- Base 동등성 검사 첫 시도는 테스트 코드가 model 필드를 Small 기본값으로
  남겨 정확한 모델 guard에서 거부됐다. 테스트의 명시적 모델 정책을 복구한
  최종 검사로 통과했다. 앱 worker의 모델 선택 실패는 아니었다.

실제 Owl3D의 연속 보간 화질, 좌우 눈의 편안함, 가림/자막/게임 조작감은
사용자 시청 확인이 남아 있다. 두 앱을 동시에 SBS 실행하면 비교가 달라지므로
기준 앱을 중지·종료하고 VFG 앱을 실행한다.
